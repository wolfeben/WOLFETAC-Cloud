## Reproducible engine finding

Step 80 attempts to finish Z208 with grade ZE2 after Z207 already created grade ZE1 for the same grower and week. The engine rejects it with:

`The record in table Pool already exists. Identification fields and values: Pool Code='ZE2E- 6-I-ZE-ZE07'`

The current generated pool key omits grade and size. The team should make the key consistent with the intended pool identity, and regression-test both grade and size differences. Existing test evidence has been preserved.

The single-week invoice cases reach `TAC Pool Consignment Post.ProcessPostedSalesInvoiceLine` and stop at its Pool Week lookup (source lines 607–609). The error is `There is no Pool Week within the filter. Filters: Season Code: '', Week No.: 0`. This run establishes the failure for the helper's normal Sales Order Ship + Invoice route; it does not establish the result of a different bespoke invoicing workflow. Pool dimensions exist on the source, but the separate posted-invoice pooling fields are blank. Those posted fields were not patched to force a pass.

The sales runner merges the customer-group dimension and synchronises both standard shortcut-dimension fields immediately before posting. The failing transaction rolls those preparation changes back, so the saved source order can still display blank shortcut season/week columns. Those standard shortcut fields and the engine's separate posted-invoice Season Code / integer Pool Week fields must not be treated as interchangeable. The team should verify the intended mapping and bespoke invoicing prerequisites before classifying the precise root cause.

The mixed-week case fails earlier in `ProcessPostedShipment`, with `Consignment No.='ZE2E-S04',Line No.='46'`. The inspected source calls `ConsignmentLine.Init()` before its next insert without resetting the primary-key Line No.; that field is AutoIncrement. Retention of the previous key is the likely cause and should be checked by the engine team. Neither the previously identified source-line-0 revenue mismatch nor the $1,200/$1,800 revenue split was reached in this run.

The unpriced test has production with no sales/consignment, and therefore does not by itself exercise a guard defined specifically for **unpriced consignment lines**. The inspected alternate `TAC Post Pool` routine checks that narrower condition. The group-close call reached G/L account validation; a complete policy test needs the agreed unpriced definition, a successful shipment and the supported close route. Do not change account 3345's shared posting setting just to make this fixture pass.
